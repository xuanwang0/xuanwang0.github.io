2026 CANN 挑战赛西北赛区初赛：SqrtSoftplusTopK 的 kernel.asc 实现解析

本文分析我参加 2026 CANN 挑战赛西北赛区初赛时实现的 SqrtSoftplusTopK 算子，重点放在提交文件 kernel.asc 的实现思路。仓库还包含题目说明、运行脚本和本地校验程序，可从项目主页查看。

下面讲解对应仓库提交 d309b05，开发环境为 Ascend 910B3 / CANN 9.0.0。赛题说明的评测环境为 A2 910B / CANN 9.0.0。本文解释代码结构与算法选择，不代表所有形状在该版本上的实测性能结论。

2. kernel.asc 的整体结构

文件可分为四层：

  1. 公共设备端辅助函数：对齐与整除、索引生成、稳定评分函数等。
  2. 若干设备端 kernel class：小行完整排序、通用完整排序、分组筛选、阈值过滤、FP16 专用选择等。
  3. 设备 kernel 入口：按 dtype 和内部策略选择对应 class 并执行。
  4. Host 入口和调度器：读取 tensor 元数据、计算 core 分配、按 shape/dtype 选择一个设备 kernel。

Host 端不读取 logits 的实际数值。即使设备端快速筛选无法证明候选范围足够，也在同一次 kernel 调用内部回退到完整排序。

3. Host 入口：元数据检查和策略分发

文件末尾的 run_kernel 从 TensorGroupInfo 读取输入 tensor 的维数、shape 和 dtype，并拒绝不符合题目约束的元数据：输入必须是二维，T 在 [1, 131072]，E 在 [64, 1024]，k 在 [1, 64] 且 k ≤ E，dtype 编码对应 FP16 或 FP32。

随后 MakePlan 决定启动多少个 core。初始 core 数不超过 T；每个 core 获得连续的一段行，行数分配采用商和余数：前 rem 个 core 多处理一行，其余处理 q 行。这使得各行只写自己的 [T, k] 输出区间。

调度器选择的策略包括：

策略 主要适用场景 核心工作
SmallRow 每核一行、专家数不超过 128、k ≤ 16 在一个 UB 工作区内排序一行
FewRun FP32 且专家数不超过 128 对最多四个 Sort32 run 做完整归并；特定边界形状可用有界前缀快速路径
SmallHalfBatch FP16、129–256 列、k ≤ 16 且每核有合适的小批量 多行共享一次向量化排序和搬运开销
Group 分组上界足以显著缩小候选集合 先排序各组最大值，再展开少量入选组
Threshold 估计候选量明显小于整行 通过阈值压缩候选；无法证明安全时完整排序
General 其余情况 在行分块内完成精确的完整排序与多级归并

部分入口还会在设备端细分。例如 FP16 通用入口可选择成对筛选；FP16 阈值入口根据列数决定条带或分块布局。分发条件只依赖 T/E/k/dtype、core 分配与资源预算，不根据输入值在 Host 上做分支。

4. 数值计算：稳定计算 sqrt(softplus(x))

公共函数 StableSqrtSoftplus 对已经选出的 logits 进行 FP32 计算。直接用 log(1 + exp(x)) 会在大正数处让 exp(x) 溢出，在很小的数处也可能因 1 + exp(x) 的舍入而丢失精度。

实现的大致步骤是：

  1. 先计算 min(x, 20)，再取指数，避免直接对很大的正数求指数。
  2. 计算 log(1 + exp(min(x, 20)))。
  3. 用上下界修正舍入结果，并对很小的指数值做下限修复，避免 log(1 + z) 在 z 很小时因消去误差被算成零。
  4. 对修正后的 softplus 取平方根。

当 x > 20 时，softplus 可近似为 x；这也是代码在避免 exp 溢出的同时保留大 logits 结果的依据。代码中另有 PositiveSqrtSoftplus，使用等价恒等式：

它只在设备端已证明输入为正、且相关快速筛选条件成立时使用；如果数据不满足正值条件，仍走完整稳定计算路径。

FP16 路径并不在 half 精度上计算 exp/log/sqrt。它将选中的 half logits 转成 float，调用同一个稳定函数，最后按输入 dtype 转回 half。排序本身可以保留原始输入精度，避免对整行额外做 FP32 转换。

5. 完整排序路径：Sort32 + 四路归并

通用精确路径由 KernelRuntimeTopK 实现。它将每行的列数补齐到适合数据搬运和排序的长度，尾部用 -inf 填充。由于填充值不可能大于真实有限 logits，它不会进入有效 top-k；并且在有 -inf 输入时，填充值与真实值相等也不会改变输出分数，因为两者评分相同。

Ascend C 的 Sort32 将输入拆成 32 元素的有序小段（run）。接下来使用 MrgSort 一次归并最多四个有序 run。多级归并时，每个子问题只保留足够的前缀：如果目标是求全局 top-k，那么任何一个子集合中排名超过 k 的元素，前面已经至少有 k 个元素不小于它，它不可能成为全局 top-k。因此各子树保留至少 k 个候选就足够；实现按 scoreSlots = ceil(k/8) × 8 等对齐长度保留前缀，最后再 gather 恰好 k 个值。

当某行包含很多个 run 时，代码按树状方式反复进行四路归并和前缀压缩，而不是一次性把整行所有记录放进一个超大排序操作中。FP32 和 FP16 共用主要排序思想，但临时记录布局和对齐方式不同。

对于较小的 FP32 FewRun 场景，还实现了一个特殊的有界前缀路径 KernelBoundedPrefixRows：它只处理满足明确条件的列数、k 和每核行数。每个 run 先取 16 个前缀，再检查被省略部分的上界是否低于最终 top-k 截止值。只有设备端检查证明所有行都安全时才接受前缀结果；被拒绝的行执行完整四路归并。其余 shape 仍走完整排序。

6. Group 策略：先选组，再选组内元素

当 E 较大而 k 相对较小时，直接排序所有 logits 的代价较高。KernelGroupSelectionLegacy 和 KernelGroupSelectionPrefetch 将每行切成若干小组，代码以 8 个元素为一组计算组最大值，然后对组最大值排序。

设最终要选 k 个元素，算法会选取至少 k 个最大组（组数按不小于 k 的 2 的幂向上取整，最少为 4）。其安全性来自一个上界：被排除组的最大值都不大于入选组最大值中的相应高位值；至少已经有 k 个入选组最大值不小于被排除组的任意元素，所以被排除组中的元素不可能进入全局 top-k。随后只从这些入选组取出 logits，再做候选排序和前缀归并。

这是一种“分层筛选”：第一层用组最大值确定哪些组有希望，第二层在留下的候选元素中精确找 top-k。KernelGroupSelectionPrefetch 是 FP32 的预取实现，使用两块输入缓冲区，在处理当前 tile 时提前搬运下一个 tile。FP16 组策略另有 native-half 实现，避免所有输入都转成 FP32 后再筛选。

组选择的收益取决于候选规模。调度器用列数、k、每组大小和候选窗口容量估算筛选后工作量；如果减少的排序工作不足以覆盖额外的分组与归并开销，就交给其他策略。

7. Threshold 策略：用阈值压缩候选，并验证容量

KernelThresholdSelection 的思路是先找一个阈值 τ，把 logits 中满足 x ≥ τ 的值压缩到候选区，再只排序候选值。阈值可以来自分组最大值中的第 k 个边界；对符合条件的 FP32 shape，代码还会先尝试估算阈值，若设备端验证未通过，再改用精确的组排序阈值重试。

候选区有固定容量 capacity，以 32 为起点，按 4 倍递增，直到容量至少为 2k。不能只假设阈值筛出的值一定装得下，所以候选过滤后会检查两类条件：

  • 容量是否溢出：候选数不能超过预留容量。
  • 候选是否足够：候选区第 k 个值不能是空位哨兵，也就是必须至少找到 k 个值。

实现还通过额外 sentinel/marker 位置检测压缩越界，而不是让候选写入静默覆盖其他 UB 区域。只有容量和第 k 个候选检查均通过，才对压缩结果排序。如果阈值估计产生候选过多或过少，会尝试精确阈值；精确阈值仍不适用时，设备端对原始整行执行完整排序。因此阈值只是省时的筛选器，完整排序是所有输入上的正确性兜底。

FP16 阈值策略针对数据布局还有条带化分支：把输入拆成若干条带，先算各条带最大值，再构造阈值候选。具体用条带还是普通分块由 shape 和 k 决定，过滤后的候选容量验证仍然在设备上执行。

8. FP16 专项：成对筛选与均值过滤

FP16 通用路径里有一类专门优化 KernelHalfMeanSelection。它把相邻两个 logits 组成一对，对每对计算最大值和最小值。先按 pair maximum 排序，保留足够多的高分 pair；若一个 pair 的最大值进入候选范围，它的另一个成员也有机会进入 top-k，因此再恢复对应 partner，把最大值与 partner 合并排序，最后取出需要的 k 个 logits。

这一步的直觉是：pair maximum 为低分的 pair，其两个成员都不可能胜过 pair maximum；把这种 pair 排除后，仍可精确保留 top-k。代码会根据列数、k 和 Sort32 run 数做成本门槛判断，只有节省的排序量足够大时才进入这条路径。

在成对排序前还有可选的 TryMeanFilter。它根据行均值和峰值提出一个候选阈值，尝试把可能的高分元素压缩到有界候选区。此过滤不是无条件成立的近似：压缩后会验证容量和第 k 个幸存值；只有证明候选完整时才采用，否则执行完整 pair 选择。若过滤同时证明用于评分的候选非负，评分可走 PositiveSqrtSoftplus；否则回到 StableSqrtSoftplus。

对很小的 FP16 k，代码还实现 KernelSmallHalfPairs；对 129 到 256 列、每核可批处理少量行的情况，实现 KernelSmallHalfBatch 或 KernelNativeHalfGroupBatch，以批量处理摊薄启动和元数据开销，并控制 32 字节 DMA 对齐。

这些路径增加了不少边界代码：原始列数可能不是 32 的倍数，half 元素与 FP32 元素的对齐单位不同，索引表也要正确换算字节偏移。因此代码在搬运时把无效尾部填成 -inf，并按实际分配空间核算 padding、partner 和候选区容量。

9. UB、分块和搬运

Ascend C 设备端主要在 Unified Buffer（UB）中处理 tile。文件定义 UB 预算为 192 KiB，并预留 4 KiB，避免把全部空间都分给输入和中间记录。每个策略根据输入 tile、排序记录、候选、索引表、临时 FP32 分数和输出缓冲区的字节数反推每次处理多少行。

分块大小还要同时满足硬件指令约束，例如 Sort32 的重复次数上限（代码按 255 次限制）、向量指令的重复数限制、DMA 32 字节对齐和 MrgSort 最多四路输入等。因而 tileRows 不是简单的固定常量，而是由 E/k/dtype 和当前算法需要的临时空间共同决定。

输入行数和列数不总是对齐。代码用 DataCopyPad 完成尾部对齐，并用 -inf 填充排序输入；输出则只写实际的 k 个值。FP32 分组路径在部分 shape 下启用双缓冲预取；其它路径也会按缓冲区生命周期复用 UB，选出 logits 后即可回收排序记录空间，供 FP32 评分和结果转换使用。

10. 正确性边界与实现取舍

代码里的快速路径可以归纳为两种安全证明：

  1. 按上界剪枝：被丢弃的组或 pair 有明确的最大值上界，并且已有至少 k 个候选不小于该上界。
  2. 按阈值压缩：设备端检查候选容量没有溢出，且第 k 个候选确实存在；否则回退到完整排序。

这两类证明让调度器可以激进地尝试减少排序规模，同时不依赖输入分布一定“友好”。特殊 shape 的快速前缀也有逐行截止值检查，只有安全行采用前缀结果。

其它关键边界包括：

  • k=1 和 k 不是 8、16、32 等对齐数的情况，索引表与输出搬运仍按真实 k 处理。
  • E 不是 2 的幂或 32 字节对齐时，尾部填充必须和实际列数区分。
  • FP16 排序保留 native half，而评分统一转 FP32，避免中间算术精度不足。
  • 仅输出分数，所以不需要把排序过程中产生的标签恢复成专家 ID。
  • 每次 run_kernel 只启动一个相应设备入口；动态候选失败后的完整排序在同一个设备 kernel 内完成，避免 Host 读取中间结果再发第二次 kernel。

总结

kernel.asc 的核心不是只实现一个 top-k，而是围绕同一个数学目标组织多条精确路径：利用评分函数单调性，先在 logits 上筛选；小规模用完整 Sort32 + MrgSort，更大的问题尝试组上界或阈值压缩，FP16 再用成对与批量路径降低排序成本。Host 端依据元数据和 UB/指令预算分发，设备端负责所有数据相关的候选验证，并保留完整排序回退。

整个实现的重点可以概括成两句话：用问题的单调结构减少必须计算和排序的数据量；每一种剪枝都要有可验证的上界或容量检查。
